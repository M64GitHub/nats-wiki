# nats-architecture-and-design (the ADR repo)

**Where NATS designs things before it builds them.** 54 Architecture Decision Records covering the
JetStream API, KV, Object Store, ordered consumers, priority groups, per-message TTL, error codes and
the cross-client contracts — the specification layer between the docs and the source.

## Where it fits

An ADR is often the **only** public statement of *why* a mechanism works the way it does, and
frequently the only place a client-side behaviour ([[ordered-consumer]], for instance) is specified
at all. It is also the source that most often disagrees with the docs, because ADRs are written ahead
of the server and revised afterwards.

Each ADR carries a metadata block: date, author, **status** (`Implemented`, `Approved`, `Proposed`,
`Deprecated`, `Partially Implemented`) and **tags**, which include the server minor a feature belongs
to (`2.11`, `2.12`, `2.14`, `2.15`) and the audience (`server`, `client`, `spec`).

## What an operator needs to know

- **Status is not a release.** "Implemented" means someone implemented it, not that every client has,
  and not necessarily in the version the tags suggest. ADR-42 is tagged `2.11` but describes the
  `prioritized` policy that shipped in **2.12** — recorded as `inbox/docs-issues.md` #7.
- **Revisions accumulate under one version tag.** The metadata `Tags` row carries a single version
  while the revision table records several, so a feature can arrive years after the ADR's date. Read
  the revision table, not the header.
- **An ADR can retract its own earlier text, in place, with no version bump.** ADR-31 does exactly
  that: "Earlier revisions of this document described the server auto-promoting `allow_direct: true`
  when [`max_msgs_per_subject` was set] … servers leave `allow_direct` untouched regardless of
  `max_msgs_per_subject`" (source: [[s-adr-31-direct-get]]). `main` is the state and there are no
  releases, so an ADR quoted from a copy taken at an older date can be quoting a claim the repo has
  since withdrawn — which is why this wiki mirrors the tarball with a fetch date and cites the
  summary, not the URL. See [[direct-get]].
- **ADRs specify client behaviour the server cannot enforce.** [[ordered-consumer]] is the clearest
  case: it is a construct clients build, so the ADR is the contract and the server sees only ordinary
  consumers.
- **When an ADR and the docs disagree, check the server.** That is this wiki's rule, and the ADR repo
  is where roughly half of those disagreements start.
