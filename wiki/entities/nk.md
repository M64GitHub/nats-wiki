# nk (nkeys)

**The key tool, and the library under every NATS identity.** NKeys are Ed25519 keypairs in a
base32 encoding whose first letter tells you what kind of entity the key belongs to. The `nk`
command-line utility lives in `nats-io/nkeys`, "Located under the nk directory" (source:
[[s-github-repo-facts]]).

## Where it fits

Below [[nsc]] and `nats auth`: those tools mint and sign JWTs, and the signing is nkeys. `nk` is
what you reach for when you need a raw key without a store around it.

| bundled in | [[nats-box]] |

**The prefix letters** — the fastest way to read a key at a glance:

| prefix | entity |
|---|---|
| `N` | server |
| `C` | cluster |
| `O` | operator |
| `A` | account |
| `U` | user |
| `P` | private key |
| `S…` | **seed** — the second letter is the type, so `SU` is a user seed, `SA` an account seed |

## What an operator needs to know

- **The seed is the only thing that must be stored.** "Generation of a seed key is all that is needed
  to be stored and kept safe, as the seed can generate both the public and private keys." Everything
  else is derivable; the seed is the secret.
- **The server never holds a private key.** "The NATS system will utilize Ed25519 keys, meaning that
  NATS systems will never store or even have access to any private keys. Authentication will utilize
  a random challenge response mechanism." This is the property that makes nkey auth safe to expose —
  a compromised server leaks no client identity.
- **Read the first letter before you debug.** A configuration that rejects a key is very often an
  `A` where a `U` belongs, or a public key pasted where a seed was wanted (`SU…`). The docs put the
  rule in one line: "If you ever see an ID which starts with an `S` … *be very careful*", and
  "Treat every `S`-prefixed string like a password" — never paste one into a ticket, a log or a
  commit (sources: [[s-docs-operator-mode]], [[s-docs-decentralized-auth]]).

## What bites

- **A lost seed is a lost identity, permanently.** "Whoever holds this one file *is* the `ACME`
  operator", and conversely "a lost seed means that identity is lost" — there is no reset path,
  because the seed *is* the private half and nothing derives it. This is why the seed, not the
  keypair, is what a backup contains (source: [[s-docs-config-and-jwt-backup]];
  [[backup-and-restore-identity]]).
- **An operator backup is a seed in cleartext unless you encrypt it.**
  `nats auth operator backup ACME acme-operator.backup` writes "a JSON document holding the
  operator's keys and JWTs", so an unencrypted archive in object storage is a full compromise rather
  than a leak. `--key` encrypts it — with **a curve NKey**, which is a different thing from the
  Ed25519 keys above and is generated by `nats auth nkey gen curve`. That curve seed is itself
  load-bearing: lose it and the archive is unreadable (source: [[s-docs-decentralized-auth]]).
- **Prefer an account *signing* key to the account identity key.** With the identity key "whoever
  holds the account's seed can issue a user with any permissions"; a scoped signing key bounds what
  its users can be given ([[subject-permissions]]). And keep at least one **operator** signing key
  offline, exposing only one to risk (source: [[s-docs-decentralized-auth]]).
- **`nats auth nkey gen`** covers the same ground from [[nats-cli]] —
  `nats auth nkey gen user --output user.nk`, `nats auth nkey show user.nk`.

## Cheat sheet

```
nats auth nkey gen user  --output user.nk     # generate a user seed
nats auth nkey gen curve --output backup.nk   # a curve key, used to encrypt operator backups
nats auth nkey show user.nk                   # show the public key for a seed
```

```
go get github.com/nats-io/nkeys                # the library the CLI wraps
```
