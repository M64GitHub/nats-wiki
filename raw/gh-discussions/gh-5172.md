## Comment — @jnmoyne (2024-03-05)

Not sure I follow the question. 
You can do either 'Core NATS subject mapping' in which case it's part of the account data (i.e. in the server's config, or in the account's JWT), and/or inside a stream's definition. They are different mappings for different purposes (in one case the subject transformation is applied as the Core NATS message is being published, while in the other case the subject transformation is applied as messages are ingested into the stream).

Also I noticed this: `ingress.iotsensor.*: "ingress.iotsensor.{{wildcard(1)}}.{{partition(1,1)}}"` -> doing a `{{partition(1,1)}} doesn't really make sense as it partitions over just one partition.

### Reply — @jnmoyne (2024-03-06)

You do not want to put the mappings you want to do inside streams (e.g. inserting a partition number) in the server config, only in the stream config. So for example you would not have a mapping for `ingress.devicetracking.*` in the server config, but in the stream listen on `ingress.devicetracking.*` and then define a subject mapping in the stream config.

For example [here](https://github.com/nats-io/nats.go/blob/52a2d33b791b6e819aacdaeef2c0b79c2cfbf81b/test/js_test.go#L2831) it defines a mapping for all the messages coming into the stream (regardless of which source or from subjects being listened to) and [here](https://github.com/nats-io/nats.go/blob/52a2d33b791b6e819aacdaeef2c0b79c2cfbf81b/test/js_test.go#L2895) it sets it as part of the source definition.

Reminder also that you need nats-server v2.10 for stream subject transforms to work.

### Reply — @jnmoyne (2024-03-07)

At the simplest level you insert the partition number in the subject in the stream transform:

source: `ingress.iosensor.*` destination: `ingress.iosensor.{{partition(10,1)}}.{{wildcard(1)}}`
- you had the order of the arguments in {{partition()}} *reversed*. It's first the number of partitions, followed by one (or more) wildcard index numbers. E.g. if you had 2 `*` wildcards in your source you could to the consistent hashing on the combined value of both those `*` wildcards with `{{partition(10,1,2)}}
- slightly more efficient to have the think you filter on higher in the subject token hierarchy, so in the destination the {{partition()}} first and then the {{wildcard()}}(s).

Then you can have 10 instances of your consuming application each one would create a JS consumer on the stream with a subject filter for the partition, e.g. for partition number 0 the consumer's filter would be `ingress.iosensor.0.>`.

And it can get a lot more sophisticated than that afterwards (yet still possible to implement in the client app code using the current features of NATS 2.10) if you need things like HA of partition consumers or administrative forms of elasticity, which is something we are currently working on (https://github.com/nats-io/nats-architecture-and-design/pull/263).
