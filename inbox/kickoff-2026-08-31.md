# Kickoff record — 2026-08-31

The decisions this wiki was configured with, and where they came from.

## Origin

The scope was cut in a conversation with Claude on the web ("scope by persona, not by product")
and confirmed here. The persona: someone who has to **run** NATS. The wiki is the solution
architect's brain, not the developer guide.

## Decisions

| question | answer |
|---|---|
| Topic | Running `nats-server` and JetStream in production |
| Pillars | core NATS · JetStream (incl. KV and Object Store) · security & multi-tenancy · topology · operations |
| Out of scope | per-language client APIs (one entity page per client), application development, commercial products beyond "where they sit", anything non-public |
| Reader | operator / solution architect holding a production problem or a design decision |
| Page types | `concept`, `internals`, `operation` (kinds: runbook, sizing, pattern), `gotcha`, `reference`, `entity` (kinds: repo, client, tool, release, product, org, person), `summary` |
| Facets | `area` (core, jetstream, kv, objectstore, security, topology, monitoring, deploy, clients, interop) and `since` (2.10, 2.11, 2.12, 2.14, 2.15) |
| Version rule | every page stating a default, limit or command carries `verified-against` + `verified-on` |
| Cheat sheets | per tool: `entity`/`kind: tool` pages plus the `### <tool>` sections of `operation` pages; topic-wide tables live in `reference/` |
| Public vs internal | **public sources only**; an internal overlay, if ever wanted, is a separate repository |
| Site name | NATS Wiki, mark `NATS WIKI` |
| Commit policy | never commit unless asked |
| Language | English |

## The question-bank question

The one open problem at kickoff was where the question bank comes from without interviewing
colleagues. Solved by mining public Q&A instead: 484 GitHub Discussions from `nats-io/nats-server`
(GraphQL API) and 257 Stack Overflow questions across three tags, filtered to operator-shaped
questions, 82 rows written with the URL of the thread where each was actually asked. Better than
recollection, because every row is citable and the mining can be repeated when the bank goes stale.

## Changes made to the shared template

`template/tools/build-site.py` in `llm-wiki-starter`: TOC table cells now render Markdown inline
instead of being escaped, so a table column can hold a link (the question bank's *asked at*
column). Selftest passed; pushed here with `tools/update-tools.sh`.

## Follow-up answers (2026-08-31, same day)

1. **The 621-key config reference: build it mechanically — yes.** `tools/fetch-docs.py` mirrors
   docs.nats.io into `raw/nats-docs/` from the site's own `llms.txt` (861 pages fetched, 0
   failed), and `tools/build-config-table.py` turns the generated `reference/config` tree into
   `inbox/config-keys-table.md` (621 keys, 179 with a documented default, 411 hot-reloadable).
   It is registered as a TOC table, so every config key is in the viewer's search. The table
   keeps a hand-written `cited by` column across regenerations — that is the coverage metric.
2. **Clients: all official ones get an entity page** — the 7 tier-1 and 5 tier-2 clients named on
   `concepts/ecosystem.md`, plus one page for the Orbit extension repos. Operator-relevant facts
   only; no API documentation.
3. **It may become official.** Kept public-sources-only and rebuild-from-source, so the wiki can
   be handed to the NATS project without an audit. Recorded in the plan's method notes.
